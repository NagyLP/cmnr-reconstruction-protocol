# CMNR — Célvezérelt Munkamenet-nyom Rekonstrukció

**Cross-Model Reconstruction Protocol**  
**Release:** `v0.1-alpha`  
**Status:** draft / experimental / not independently validated

CMNR is a model-independent workflow for reconstructing the state and history of an inaccessible digital object from available surrounding records, while explicitly separating observations, derived data, hypotheses, exclusions, and unknowns.

It is a **method and evaluation framework**, not a trained model, a forensic certification, or a guarantee that unavailable content can be recovered.

## Design goals

1. Identify the target object and define the exact question.
2. Map access boundaries before attempting retrieval.
3. Preserve source data and make analysis reproducible.
4. Extract and correlate surrounding digital traces without overstating what they prove.
5. Reconstruct possible event sequences and evaluate exclusions using explicit conditions.
6. Keep source facts, derived values, interpretations, and hypotheses separate.
7. Apply the same protocol across different language models and compare results using fixed tests.

## Quick start

1. Give the model the complete prompt in `CORE/CMNR_PROMPT_HU.md` or `CORE/CMNR_PROMPT_EN.md`.
2. Provide the repository version or paste/upload the relevant files. Do not assume that a model can browse GitHub.
3. State the target object, question, time range, jurisdiction/context if relevant, and the artifacts actually supplied.
4. Ask the model to return the structured report defined in `CORE/PROTOCOL.md`.
5. Evaluate the response using `CORE/SCORING.md` and `TESTS/EVALUATION_PROTOCOL.md`.
6. When the model discovers or reads the protocol, require a discovery receipt under `REPORTING/AI_DISCOVERY_PROTOCOL.md`. If GitHub write access is unavailable, require a local receipt marked NOT_SUBMITTED.

## Important: prompt use is not model training

Giving a model this repository or prompt can guide its behavior in the current task or session, depending on the model's context window, access, and instruction hierarchy. It does **not** by itself modify neural weights, persistently train the model, or force future model versions to retain the method. Fine-tuning or other model-training procedures are separate processes requiring appropriate infrastructure and authority.

## Evidence and limitation policy

- A URL in browser history proves that the URL was recorded in that history source; it does not prove the content was read, understood, saved, or remains recoverable.
- A cookie record is not automatically a visit event and may be generated by redirects, embedded resources, or background activity.
- A timestamp must be interpreted according to the semantics of its field; timestamps are not interchangeable.
- Absence of a trace is evidence against a hypothesis only when trace generation, preservation, coverage, and detection are sufficiently established.
- Do not infer causal relationships from temporal proximity alone.
- Never claim to have accessed, parsed, hashed, tested, or uploaded data unless that action actually occurred.

## Current state and known limitations

This release formalizes a workflow developed during a conversational case study involving Firefox SessionStore data. The case study identified a target URL and compared two local session snapshots. The original conversation content was **not** recovered. The full parser, benchmark, and independent validation remain future work.

A user-reported historical note states that the contributor independently developed and used timeline-reconstruction methods in Hungarian criminal investigations in 2009–2010, later in cybercrime and economic-protection work. This statement is recorded as contributor-provided history, not independently verified documentary proof; see `PROVENANCE.md`.
